01 / System map

One authority. Clear failure boundaries.

Production topology shown below. Select a flow to trace behavior; select any component for its role. The semester pilot stays on one host with off-host backups.

Institutional productionMultiple application instances and database replicas protect against host failure. Independent physical placement, fencing, redundant ingress, and tested recovery are required; container replication alone is insufficient.

Scope: outcome measurement and reporting. OBS remains the source for institutional records; EYS/LMS retains learning content. No GPU, sharding, or new analytical database is required for the initial design.

DEFER / CACHE

Optimize the read path first

Index scoped selectors, paginate evidence, eliminate N+1 queries, and precompute published results before adding a shared cache.

CONDITIONAL / MESSAGING

RabbitMQ when jobs demand it

For a larger independent queue workload, use quorum queues, confirms and acknowledgements. Consumers still need idempotency.

CONDITIONAL / ANALYTICS

ClickHouse for event-scale queries

Consider a separate analytical system for broad LMS telemetry or scans that demonstrably disrupt the transactional workload.

03 / Capacity laboratory

Make the assumptions editable.

Decimal GB throughout. Storage uses eight assessments, six LOs, eleven possible POs, three grade revisions, and a provisional 3× physical allowance.

What creates the bytes?

E = students × enrollments per year Grades = E × 8 × 3 revisions × 500 B Scores = runs × (E × 17 + students × 11) × 300 B Evidence = runs × (E × 42 + E × 11) × 400 B Manifests = runs × E × 8 × 700 B

42 = eight assessments × three LO links + six LOs × three PO links. Every retained run is modeled as a full-population equivalent. Actual per-course reruns may differ.

Evidence dominates. Retaining 52 runs/year increases baseline logical growth from 9.16 to 109.72 GB/year. Approve draft expiry and published-evidence retention explicitly.

04 / Reliability

Protect both the bytes and their meaning.

Replicas cover specified infrastructure failures. Immutable inputs, authorization, and a publication gate protect academic correctness. Backups cover a different failure class.

Publication protocol

Enqueue durably

Record scope, expected revision, and idempotency key.

Capture and calculate

Freeze consistent inputs; calculate with Decimal and fixed policy versions.

Persist and validate

Write scores and evidence in bounded batches. Partial output remains unpublished.

Publish atomically

Reauthorize; lock input guards and publication series; compare current versions and hash.

Preserve history

Conflicts return 409. The prior valid publication stays readable.

Recovery objectives

Failure / targetProposed objective
Production availability99.9% monthly · 43.2 min budget / 30 days
Primary host lossRTO ≤5 min after tested failover
Acknowledged synchronous commitsRPO 0 within validated failure model
Complete site lossRPO ≤5 min · RTO ≤60 min after rehearsal

Strict synchronous durability means writes stop if no eligible synchronous standby remains. Do not silently weaken durability to keep writes available.

165 GB at 100 MB/s takes ≈28 minutes to transfer alone. Provisioning, WAL replay, validation, and traffic switching must fit within the remaining recovery time. Replication does not replace backups.

Name an incident commander, operator, and communications owner. Monitor outside application hosts. Record detection, impact, mitigation, recovery checks, and follow-up ownership.

05 / Deployment plan

Earn each additional component.

Advance on measured evidence rather than enrollment alone. These are proposed gates, not claims that the repository already implements the design.

01 / SEMESTER PILOT

One reproducible installation

Compose · Django · PostgreSQL · private files · encrypted off-host backup.

  • 4 vCPU / 8 GB starting host
  • Canonical scoring and scoped-access checks
  • Bounded imports and calculations
  • Successful isolated restore
Gate: correctness + recoverability
02 / INSTITUTIONAL ROLLOUT

Independent failure domains

Two application VMs · three DB VMs · durable workers · institutional storage.

  • Apps: 4 vCPU / 8 GB each
  • DB: 4–8 vCPU / 16–32 GB each
  • DB: 400–500 GB usable SSD each
  • 325 req/s target; stress toward 1,040
Gate: load + failover + restore
03 / MEASURED EXPANSION

Isolate the proven bottleneck

Add an analytical store, broker, cache, or capacity when benchmark evidence supports it.

  • Record p50/p95, queries, locks, pool waits
  • Measure evidence persistence and memory
  • Track bytes per row, index size, WAL/day
  • Reassess each new service's operating cost
Gate: demonstrable benefit
